# sqlite-vector-rs v0.3.0 Improvements Design Spec

Fixes and extensions to the `vector` virtual table based on the 2026-07-11
review, which reproduced six correctness bugs against the built extension and
identified an O(N) per-commit write-amplification problem. Three phases:
correctness, efficiency, completeness. Each phase leaves the crate shippable.

**Versioning:** v0.3.0. The shadow-table format may change without a migration
path — no deployed users exist.

## Confirmed defects driving this spec

All reproduced in the `sqlite3` CLI against `target/debug/libsqlite_vector_rs.so`:

| # | Defect | Symptom |
|---|--------|---------|
| B1 | `UPDATE` delete+reinserts without the id (`src/vtab/mod.rs` `update_data_shadow`) | Row id 1 became id 4; KNN for the updated vector silently omitted it (index key orphaned) |
| B2 | Explicit rowid ignored on INSERT (`xUpdate` never binds `args[0]`/`args[1]`) | `INSERT INTO t(id, vector) VALUES (42, …)` inserted as id 2 |
| B3 | Rollback with `last_committed == None` keeps phantom index keys (`src/vtab/transaction.rs`) | After `BEGIN; INSERT ×3; ROLLBACK` on a fresh connection, all later inserts fail: "Duplicate keys not allowed" |
| B4 | Metadata read back via `get_blob` (`src/vtab/cursor.rs`) | `typeof(label)` = `blob`; `WHERE label = 'a'` matches nothing |
| B5 | `best_index` consumes LIMIT as k unconditionally | `ORDER BY distance DESC LIMIT 2` returned the two *nearest* rows; filters shrink results below LIMIT |
| B6 | `vector_rebuild_index` passes `None` for HNSW params (`src/scalar.rs`) | Rebuild silently discards the table's configured m/ef_construction |
| B7 | `bytemuck::cast_slice` on `&[u8]` (throughout) | Latent panic on misaligned blobs; works today only because malloc returns 16-byte-aligned blocks |

Performance: serializing the whole HNSW graph on every dirty commit made 2,000
autocommit inserts ~10× slower than the same inserts in one transaction, and
the gap grows linearly with N·dim per commit (quadratic in total).

## Goals

1. Correct SQL semantics: UPDATE, explicit rowids, rollback/savepoints,
   metadata filters, ORDER BY/LIMIT — all behave like a native table.
2. Write throughput independent of table size.
3. Practical parity with sqlite-vec/vectorlite where it matters: filtered KNN,
   exact search, runtime tuning, vector utility functions.

## Non-goals

- Cross-connection index coherence. One writer per table at a time; the
  in-memory index on other connections is stale until reconnect. Concurrent
  writers are last-write-wins on the graph blob, but `_data` never loses rows
  (it is ordinary transactional SQLite). Documented, not fixed.
- Bit/binary vector type and hamming distance.
- Arrow import/export of metadata columns.
- WAL multi-writer graph merging.

## Phase 1 — Correctness

Every fix starts with a failing end-to-end SQL test (rusqlite loading the real
extension) reproducing the CLI repro from the review. Ordering within the
phase follows the list below; B1/B2/B3 touch the same files and land first.

### 1.1 UPDATE preserves rowid (B1)

Replace `update_data_shadow`'s delete+reinsert with a real SQL UPDATE:

```sql
UPDATE "<t>_data" SET vector = ?, <meta…> = ? WHERE id = ?
```

Handle the rowid-changing case: when `info.args()[0]` (new rowid) is non-NULL
and differs from `info.rowid()`, the UPDATE also sets `id = ?`, and the index
entry is re-keyed (`remove(old)` + `add(new)`). Otherwise the index entry for
the unchanged rowid is `remove` + `add` with the new vector, as today.

### 1.2 Explicit rowid INSERT (B2)

In the insert arm of `xUpdate`: if the new-rowid arg (or the `id` column
value) is non-NULL, include `id` in the INSERT column list and bind it; return
that rowid. A duplicate id surfaces as SQLite's native constraint violation.
NULL keeps today's auto-assignment.

### 1.3 Rollback and savepoint safety (B3)

- `init()` populates `IndexState.last_committed` immediately after creating or
  loading the index (serializing an empty or freshly-loaded index is cheap).
  `rollback()` therefore always has a snapshot; the `None` branch disappears.
- `savepoint(n)` pushes `(n, serialized_index)` onto a snapshot stack in the
  transaction object; `release(n)` pops entries ≥ n; `rollback_to(n)` restores
  the snapshot for the smallest entry ≥ n and truncates the stack. Memory
  cost is bounded by savepoint nesting depth and accepted; savepoints inside
  bulk loads are rare.

### 1.4 Metadata type fidelity (B4)

`ScanRow`/`KnnRow` store metadata as owned dynamic SQLite values (sqlite3_ext's
owned `Value`, which preserves NULL/INTEGER/REAL/TEXT/BLOB), not
`Option<Vec<u8>>`. `column()` passes the value through so `typeof()` and all
comparisons behave as declared. Inserts already bind `ValueRef`s as-is; no
change on the write path.

### 1.5 LIMIT/ORDER BY correctness in best_index (B5)

- Inspect `IndexInfo` order-by: if it is exactly `distance ASC`, call
  `set_order_by_consumed(true)`.
- Consume the LIMIT constraint as k **only when** the order-by is consumed (or
  absent) **and** every other usable constraint has been handled by us.
  Otherwise ignore the LIMIT (leave it to SQLite) and search with the default
  k. Wrong results become impossible; Phase 3 restores speed for the filtered
  case.
- Document the default k (100) in the README and make it a named constant.

### 1.6 Persisted table config + rebuild fidelity (B6)

- Wire up the currently-dead `save_meta_to_shadow`: at `create()`, write a
  `meta` row into `_index` containing JSON
  `{dim, type, metric, m, ef_construction, ef_search, sync_every, mode}`.
- `connect()` prefers the persisted meta over re-parsed args when both exist
  (they should agree; mismatch is an error).
- `vector_rebuild_index(table)` drops to one argument and reads the meta row,
  building with the table's actual params. The old 3-arg form is removed.

### 1.7 Alignment robustness (B7)

Replace every `cast_slice::<u8, T>` on blob data with `try_cast_slice`,
falling back to an unaligned copy (`pod_read_unaligned` per element or a
byte-wise copy into an aligned buffer) when alignment fails. Add a unit test
that feeds a deliberately misaligned buffer (offset subslice) through
`compute_distance` and `HnswIndex::add`.

## Phase 2 — Efficiency

### 2.1 Lazy graph persistence with reconcile-on-connect

Today `xSync` rewrites the whole serialized graph on every dirty commit.
New model:

- `IndexState` gains `changes_since_persist: u64`.
- New table param `sync_every=N` (default **1024**; `sync_every=1` restores
  per-commit persistence). `xSync` persists only when
  `changes_since_persist >= sync_every`; it always remains transactional with
  the enclosing commit when it does run.
- New scalar `vector_sync_index(table)` forces a persist (for use before
  closing or handing the file to another process).
- The persisted `_index` payload becomes two rows: `hnsw_graph` (blob) and
  `graph_state` (JSON `{row_count, max_rowid}` captured at persist time).
- **Reconcile on connect:** load the graph blob, then compare with `_data`:
  1. For each `_data` row with `id > max_rowid` or `!index.contains(id)`,
     add its vector to the index (covers commits after the last persist).
  2. After additions, if `index.len() != count(_data)`, the graph contains
     stale keys (deletes lost since last persist) → rebuild the index from
     `_data` rows entirely.
  Either way the connection starts consistent; `_data` is always the source
  of truth because it is ordinary transactional SQLite.

Rollback interaction: `last_committed` snapshots (1.3) are taken on persist,
not on every commit. `rollback()` restores the last snapshot **and then
replays** the reconcile step against `_data` (same code path as connect), so
a rollback after unpersisted commits does not lose those committed rows.

### 2.2 Streaming full scan

`filter()` in scan mode holds the prepared `SELECT` statement in the cursor
and advances it in `next()`, instead of materializing every row into a Vec.
`eof` reflects statement exhaustion. KNN mode keeps materialized results
(bounded by k).

### 2.3 Prepared-statement caching

The vtab owns a small statement cache (insert, insert-with-id, update,
delete, fetch-by-id), created lazily and reused across calls. The KNN row
fetch reuses one cached statement across all k hits instead of preparing per
hit. SQL string `format!` happens once per table, not per operation.

### 2.4 Allocation-free distance conversions

`compute_distance` and the f16/i16/i32 arms of `HnswIndex::{add, search}`
stop building intermediate `Vec<f32>` where possible: distance loops zip the
two typed slices and convert per element inside the accumulation. (usearch
`add`/`search` still require a contiguous f32 buffer for non-native types; a
single reusable scratch buffer per call site is acceptable there.)

### 2.5 Throughput regression test

An integration test inserts 2,000 rows in autocommit mode and asserts wall
time within 3× of the same inserts in one transaction (generous bound; the
current code is ~10×). Guards against reintroducing per-commit O(N) work.

## Phase 3 — Completeness

### 3.1 Filtered KNN

- `best_index` accepts equality and range constraints on metadata columns in
  a KNN plan: assigns them argv indexes, does **not** omit them (SQLite still
  re-checks), and encodes which columns/ops arrived via `index_str`.
- `filter()` applies those constraints in the row-fetch SQL (`WHERE id = ?
  AND label = ?…`) and oversamples the ANN search: start at
  `k' = max(4k, k+16)`, double until k rows satisfy the constraints or
  `k' >= index.len()` (terminal: full index scanned).
- With this in place, the LIMIT constraint may again be consumed in filtered
  queries (revisits the conservative 1.5 rule): consumed LIMIT = target k for
  the oversampling loop.

### 3.2 Exact search mode

- New table param `mode=hnsw|exact` (default `hnsw`, persisted in meta).
- `mode=exact` skips usearch entirely: no in-memory index, no graph blob, no
  dirty tracking; transactions are pure `_data` operations. KNN queries run a
  streaming brute-force scan over `_data` with a bounded top-k
  binary heap, computing exact distances via `compute_distance`. Identical
  SQL surface (`knn_match`, `distance`, LIMIT, filters — filters apply
  directly in the scan SQL, no oversampling needed).
- Intended for small-to-medium tables and correctness-sensitive queries;
  README gives guidance (exact is typically fine below ~100k rows × 768 dim).

### 3.3 Runtime tuning and introspection

- `vector_ef_search(table, n)` — updates the live index via usearch's
  expansion-search setter and rewrites the persisted meta. Takes effect for
  subsequent queries on this connection; other connections pick it up from
  meta on reconnect.
- `vector_index_info(table)` — returns JSON:
  `{rows, dim, type, metric, mode, m, ef_construction, ef_search,
  sync_every, changes_since_persist}`.

### 3.4 Vector utility scalar functions

All type-dispatched over the existing `VectorType`, mirroring current scalar
registration:

| Function | Semantics |
|----------|-----------|
| `vector_normalize(blob, type)` | L2-normalize; error on zero vector; int types promoted to float4 output |
| `vector_add(a, b, type)` / `vector_sub(a, b, type)` | Element-wise; dimension mismatch is an error |
| `vector_scale(blob, factor, type)` | Multiply by REAL scalar |
| `vector_slice(blob, type, start, end)` | Half-open element range; bounds-checked |
| `vector_quantize_int8(blob, 'float4')` | Symmetric max-abs scaling f32 → i8; returns the int1 blob |

### 3.5 Documentation

README updates: quoted multi-column metadata syntax
(`metadata="label TEXT, score REAL"` — SQLite splits unquoted args on
commas), `sync_every` and `vector_sync_index`, `mode=exact`, default k,
int2/int4 f32-precision caveat (lossy above 2^24), and the single-writer /
stale-reader limitation from Non-goals.

## Testing strategy

- **End-to-end SQL tests are the correctness authority.** Each B1–B7 defect
  gets a test that executes the exact failing SQL from the review through
  rusqlite + the loaded extension and asserts the correct result. Existing
  unit tests (pre-split args, SQL string equality) remain but no longer stand
  in for behavior.
- New behavior tests: rowid-changing UPDATE, savepoint/rollback_to nesting,
  crash-recovery reconcile (kill persistence by skipping `vector_sync_index`,
  reopen, verify KNN completeness), filtered-KNN returns exactly k rows,
  exact-vs-hnsw result parity on small tables, and each utility function's
  happy path + error cases.
- Throughput regression test per 2.5.
- Full matrix (6 types × 3 metrics) stays covered by the existing
  `type_matrix_test.rs`, extended to run under both `mode=hnsw` and
  `mode=exact`.

## Implementation order

Phase 1 (1.1 → 1.7) → Phase 2 (2.1 → 2.5) → Phase 3 (3.1 → 3.5). Within each
phase, items are independently landable except: 1.6 precedes 2.1 (meta row)
and 3.1 revisits 1.5's LIMIT rule. Tag v0.3.0 after Phase 3; a mid-point
release after Phase 1 is optional if a safe crate is needed sooner.
